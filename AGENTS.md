## Creator payouts and Paystack splits

- Creator payout onboarding registers each teacher's Kenyan bank details with Paystack as a subaccount. Bank names/codes come from Paystack's `/bank?currency=KES` endpoint. New full account numbers are sent server-to-server to Paystack, then discarded; AdventSkool stores only the Paystack subaccount code and the last four digits. The subaccount code is server-only.
- Apply `supabase/migrations/0014_creator_payouts.sql` and `0015_paystack_creator_splits.sql` before deploying payout features. Migration 0015 masks and clears raw account numbers from the earlier payout form; affected teachers need to resubmit their bank details to create a Paystack subaccount.
- Admin verification is required after Paystack registers a subaccount. Only profiles marked verified/ready get split parameters at course checkout. Checkout snapshots the rate, amount, fee mode, and routing mode onto the payment before redirecting, so later settings changes affect future checkouts only.
- Paystack subaccount `percentage_charge` is kept equal to AdventSkool's commission percentage (the platform's share); creator-specific rates are synced when saved/verified, and default-rate changes update subaccounts without an individual override. New subaccounts are created with the effective platform rate. If Paystack cannot accept a rate update, the local rate/verification change is not saved. At checkout, the exact commission amount is also passed as a KES minor-unit `transaction_charge`, which overrides the subaccount percentage for that sale. `fee_mode=inclusive` sets Paystack's fee bearer to `account` (AdventSkool); `fee_mode=exclusive` sets it to `subaccount` (creator). Customer checkout amounts stay as currently calculated. Paystack's transaction verification fee is stored on the earnings ledger.
- Split-mode earnings are marked routed after verified customer payment. This means Paystack accepted the allocation; it is not proof that the creator's bank has settled. Confirm settlement in Paystack's settlement reports. Historical and platform-only earnings are not automatically transferred by this integration.
- The account must have live Paystack API credentials, a configured platform settlement account, and Paystack subaccount/split functionality enabled for KES. Confirm feature access with Paystack if subaccount creation or split initialization is rejected. Test in Paystack test mode first, then deploy the same flow with live keys and verify one low-value transaction and its settlement report.
- Standard creator payout terms are a 10% AdventSkool commission with Paystack processing fees charged to the creator (`fee_mode=exclusive`). Migration `0017_creator_payout_defaults.sql` sets this platform default; creator-specific overrides remain as saved. The public `/creator-payout-agreement` page documents the terms and directs special deal requests to `adventskool@gmail.com`; special arrangements apply only after written confirmation and settings update. Apply migration 0017 before deploying this default change. Existing commission overrides are not overwritten.
- Existing students can apply from the public “Teach & sell” link using their existing account, or new creators can register through `/register/creator` using the student signup UI with WhatsApp added. Creator accounts can create courses/products while pending admin review; checkout keeps sales platform-only until creator approval and payout verification. Admin user controls allow rejecting applications, timed suspension, restoration, and account deletion. Suspended sessions are denied by authenticated API routes until suspension expiry. Creator onboarding supports payout setup later; the teacher dashboard prompts creators who have published without payout details.
- Admin creator operations are available at `/dashboard/admin/creator-applications` and `/dashboard/admin/users`. The application page filters pending versus all applications, shows applicant WhatsApp and decision status, and approves/declines through the admin users API. Submissions through `/api/creator/application` and new creator registrations notify administrators in the dashboard notification feed; review decisions notify the applicant. New creator signups collect one required Kenyan WhatsApp number, stored as the profile contact phone and WhatsApp number. The users page includes account totals, role filtering, and name/email search while retaining edit, delete, suspension, and restoration controls. Apply migration `0018_creator_application_notifications.sql` to enable notifications for creator registrations made through the signup flow.
- Email signup blocks a maintained list of common disposable email domains in the client registration service. Supabase email confirmation should remain enabled to ensure applicants verify ownership; the disposable domain block is not a substitute for configuring email confirmation or a maintained disposable-email provider.
- `PAYSTACK_SECRET_KEY` stays server-side. Never expose it, the Paystack subaccount code, or a full bank account number to browser code, logs, client responses, or git. Payout endpoints use the service-role client; authenticated browser clients have no direct table access to payout account data.

## Wealth Academy module

- Wealth Academy is a full parallel digital marketplace alongside Digital Products (designs). It lives at `/wealth`, uses an **emerald** accent (designs use indigo), and teaches money mindset, wealth generation/preservation, family wealth, and eradicating generational poverty. It is intentionally isolated — it never reads or writes the design tables; only additive edits were made to shared files.
- Backed by its own tables in `supabase/migrations/0019_wealth_academy.sql`: `wealth_products` and `wealth_orders`, plus enum `wealth_order_status`, RLS policies, and RPC `increment_wealth_product_views(uuid)`. Migration `0020_wealth_creator_access.sql` adds per-creator Wealth permission (off by default), creator-scoped RLS, and the admin-controlled public navigation setting. **Apply migrations 0019 and 0020 to Supabase before deploying.**
- Public flow mirrors designs: catalog `app/(public)/wealth/page.tsx` → detail `app/(public)/wealth/[productId]/page.tsx` → `POST /api/wealth/checkout` (Paystack) → `POST /api/wealth/verify` (calls `fulfillWealthOrder`) → `GET /api/wealth/download` proxy and `GET /api/wealth/orders/[id]/status`; reader proxy `GET /api/wealth-products/[orderId]/read`. Purchased resources appear in the dashboard library `app/dashboard/wealth/page.tsx` with a reader at `app/dashboard/wealth/[orderId]/read/page.tsx`.
- Admin management lives at `app/dashboard/admin/wealth` (list/publish/delete and public navigation visibility), `.../create`, `.../[productId]/edit`, and `.../orders`. Admins grant approved creators Wealth authoring per account from the Users page; it is disabled by default, and migration 0020 enforces it in RLS. Enabled creators manage only their own resources at `app/dashboard/teacher/wealth`. The public Wealth Academy navigation and search visibility is a separate global admin setting; hiding it removes those discovery links but does not disable direct URLs or purchasing.
- Code layout mirrors designs: `types/wealth.ts` + `types/wealthOrder.ts`, `services/wealthService.ts` + `services/wealthOrderService.ts`, `lib/wealth/{server,fulfill,downloadUrl,pdfPreview,access}.ts`, and `components/wealth/*`. - Wealth email templates (`wealthOrderAdminEmail`, `wealthOrderCompletedEmail`) live in `lib/email/templates.ts`. `PublicNavbar` (nav link + global search), `Footer`, `dashboard/Sidebar`, `app/sitemap.ts`, and `CatalogFilterBar` (emerald accent) are wired for wealth. `ShareButton.entityLabel` now also accepts `"Resource"`.
- Categories live in `types/wealth.ts` (`WEALTH_CATEGORIES`) and cover foundations, mindset, budgeting/saving, debt freedom, investing basics, wealth generation/preservation, family wealth & legacy, estate/inheritance, eradicating generational poverty, financial literacy for kids, business, real estate, retirement, and faith & stewardship.

## Documentation handbook

- The canonical internal documentation is the handbook at `/dashboard/admin/documentation`, admin-only (enforced by the `/dashboard/admin` prefix rule in `middleware.ts` plus `useRoleGuard(["admin"])` in `components/dashboard/HandbookViewer.tsx`). It explains what the platform is for, what is sold, how creators receive money, the operating model, policies, and FAQs, and it is downloadable as a PDF.
- All handbook copy lives in one place: `lib/handbook/content.ts`. It exports `HANDBOOK_META`, `HANDBOOK_SHORT_DESCRIPTION`, `HANDBOOK_LONG_DESCRIPTION`, `HANDBOOK_FACTS_AT_A_GLANCE`, `HANDBOOK_SECTIONS`, and `handbookToMarkdown()`. Never duplicate handbook prose into components, pages, or API responses — edit the content module and every output stays in sync.
- Three outputs are generated from that one source: the on-screen document (`components/dashboard/HandbookDocument.tsx`), the printed "Save as PDF" output, and the Markdown export (`adventskool-handbook.md`). The Markdown export is the intended grounding or fine-tuning corpus for AI assistants about AdventSkool, and chapter 18 is written as a grounding brief with authoritative facts, a glossary, approved answers, and claims the assistant must never invent.
- PDF generation is browser print, not a server-side PDF library: no PDF dependency is installed and none should be added. "Download PDF" calls `window.print()` after pointing `document.title` at the handbook title so the print dialog suggests a sensible filename, and it shows a `StatusCard` telling the admin to choose "Save as PDF".
- Print styling lives in the `@media print` block at the end of `styles/globals.css`, scoped with `body:has(.handbook-doc)`. It hides the dashboard chrome (`header`, `aside`, `nav`, and any `.no-print` element), flattens the saved dark theme to ink-on-paper, and applies page-break rules. `HandbookDocument` therefore must not render `<header>`, `<nav>`, or `<aside>` — use `div`/`section` with `role="note"` for callouts — or that page will be hidden when printing. Chapters and tables carry `handbook-chapter` / `handbook-table-scroll` hooks for those rules.
- When commissions, fee modes, product lines, roles, or published policies change, update the relevant chapter in `lib/handbook/content.ts` in the same change so the handbook, the PDF, and the AI training data describe the deployed system.

## UI feedback, loading, and navigation conventions

- **Always show a loading state to the user.** Never keep an action silent. For page loads, use `<PageSkeleton>` (with an accessible `label`) and `loading.tsx` files for routes. For button/form actions, pass `loading`/`loadingText` to `<Button>` or use `useAsyncAction` so the button is disabled, shows a spinner, and announces `aria-busy`.
- **Separate feedback from the page.** Use `<StatusCard>` for loading, success, error, warning, and info. Messages must appear in a raised, tinted card (not inline paragraph text that blends in). Use the `role`/`aria-live` that `StatusCard` provides (assertive for errors).
- **Block double submits.** Use `useAsyncAction` for any user-initiated request (forms, clicks). It ignores extra clicks while in flight. When you need manual state, set an explicit `isLoading` boolean and disable the trigger.
- **Route transitions are visible.** Mount `<RouteProgress>` in the root layout so all client-side navigations show the top progress bar (handled for `<Link>` clicks and for `useAppRouter`'s `push/replace`).
- **Consistent UI primitives.** Use shared components: `Card`, `CardHeader`, `CardBody`, `StatCard`, `Badge`, `Field`, `Input`, `Select`, `Button`, `Spinner`, `Skeleton`, `PageSkeleton`, `StatusCard`.
- **Icons: `lucide-react` only.** It is the house icon set and the only icon dependency. Do not add `react-icons`, Heroicons, Radix icons, or Font Awesome. Navigation link definitions (`PublicNavbar.navLinks`, `dashboard/Sidebar.linkMap`) each carry an `icon: LucideIcon` field that both the desktop and mobile/drawer renders draw from, so icons stay in sync automatically. Do not hand-inline raw `<svg>` markup; convert any that exist to lucide components.
- **Public nav account control.** `PublicNavbar` is the single public header (mounted in `app/(public)/layout.tsx`, so it covers every public route). It reads `useAuth()` and renders a three-way account control: a pulse placeholder while `authLoading`, a `CircleUser` profile button linking to `/dashboard/${profile.role}` when a profile exists, and the `Log in` link otherwise. Never render an unconditional `Log in` link here — a signed-in user must never see it. Both the desktop header and the mobile drawer implement this, plus `aria-current="page"` active states via `isNavActive`.
- **Data fetching pattern.** Prefer `useAsyncData` for page loads (always exposes `isLoading`, `errorMessage`, `reload`). Prefer `apiRequest<T>` for browser fetches — it parses JSON and throws the server's `error` message so failures are never silent.
- **Put these rules in memory.** Every new page must have a loading state (skeleton or status card), and every action that waits on the network must block repeats and display success/error in a distinct `StatusCard`. Apply these conventions to existing pages when you touch them.

## Mobile layout and overflow

- Every dashboard page and shared header control must fit narrow phone viewports without horizontal page scrolling or clipping. Use `min-w-0` on flex/grid children that contain text, allow long labels and prices to wrap, and stack cards/actions when side-by-side content no longer fits.
- Search results and notification panels must stay within the viewport, scroll internally when their content is long, and wrap long notification text. Check responsive behavior at a narrow mobile width whenever changing dashboard listings or header controls.

## Dark mode contrast rule

- The theme is selected by toggling the `.dark` class on `<html>` and saved as `adventskool-theme` in local storage. Tailwind's `dark:` variant must therefore use the class selector (`@custom-variant dark (&:where(.dark, .dark *));` in `styles/globals.css`); never rely on the device's `prefers-color-scheme` to activate app dark mode.
- Every visible text label, heading, icon, border, input, selected state, and fixed navigation surface must retain readable contrast in both themes. Avoid hardcoded light-theme foregrounds/backgrounds on dark surfaces; add paired `dark:` styles or use the theme variables. Include `text-slate-950` in dark public-shell overrides when appropriate.
- When touching theme styling, check the full affected screen and shared navigation, including mobile bottom navigation and dashboard sidebars/menus. Verify category/section headings, cards, footer attribution, cart, creator agreement, form controls, and overlays where present; do not fix only the first clipped or low-contrast word.

## AdventPay invoicing

- AdventPay is the account-based invoicing module. Its standalone product routes are `/adventpay`, `/adventpay/login`, `/adventpay/signup`, `/adventpay/dashboard`, and `/adventpay/admin`; they use their own header, footer, authentication entry points, and focused dashboards. `/advent-pay` remains only as a redirect for legacy links. Authenticated users see their own invoices, pending balance, next due date, Till instructions, payment history, and post-settlement PDF receipt downloads.
- Administrators manage invoices at `/adventpay/admin` (the legacy `/dashboard/admin/advent-pay` still works): they set Till details, create invoices for registered accounts, choose one-time or recurring billing with a weekly/monthly/quarterly/yearly interval, edit unpaid invoices, correct a paid receipt's custom “Received from” name/email and optional note, cancel unpaid invoices, and manually confirm Till payments. Recurring schedule metadata does not automatically issue or charge future invoices; issuing each future invoice remains an explicit administrator action. Issuing, cancelling, and confirming invoices creates an in-app notification for the customer.
- Apply migrations `0024_advent_pay.sql` and `0025_adventpay_invoicing.sql` before deployment. Migration 0025 adds billing type/interval and receipt recipient/note fields. Till details are snapshotted onto each Till invoice so later settings edits never alter already-issued payment instructions. Paid invoice financial values and paid receipt records are retained for audit: only display recipient/name/email/note corrections are allowed after payment; paid invoices cannot be deleted.
- Paystack AdventPay transactions use `ap_` references. Customer checkout starts at `/api/advent-pay/invoices/[id]/pay`, returns to `/adventpay/dashboard`, is verified server-side at `/api/advent-pay/verify`, and is also fulfilled through the existing signed Paystack webhook. A confirmed Paystack or admin-confirmed Till payment receives a real PDF download from `/api/advent-pay/invoices/[id]/receipt`; it is generated server-side without exposing payment credentials. `PAYSTACK_SECRET_KEY` remains server-only.
- AdventPay dashboard notifications are available from the bell in the standalone AdventPay header. Invoice creation, cancellation, and confirmed payments write the customer notification feed; the bell lets users read, open, and mark those notices read without leaving AdventPay.
- The AdventPay invoice API paginates and filters server-side (`page`, `pageSize` up to 100, `status`, and `billingType`), so the customer history and admin register do not download the full ledger. Both views provide paid, pending, overdue, and recurring quick filters; the register uses 25-row pages. Apply `supabase/migrations/0026_adventpay_register_performance.sql` after 0025 before deployment to add the supporting indexes for large registers.

## Creator storefronts and custom-domain requests

- Creator storefronts use the canonical public URL `https://adventskool.co.ke/@handle`. Migration `0021_creator_storefronts.sql` adds unique creator handles, optional bio/social fields, storefront query indexes, and a manual custom-domain request queue. Apply migration 0021 before deploying this feature.
- Every teacher receives a generated unique handle; creators can edit it from `/dashboard/teacher/storefront`. Old handles are retained as aliases and permanently redirect to the current storefront so previously shared links keep working. The creator name is the only required public-profile field. Profile picture, bio, and individual social links are omitted completely from the public page when empty.
- Public storefronts combine the creator's published courses, Digital Products, and Wealth Academy resources without combining or cross-writing their underlying tables. Product share actions on the storefront link back to the exact product card at `/@handle?product=<kind>-<id>#product-<kind>-<id>`. Recommendations appear after the creator catalogue and exclude the current creator.
- Creators submit a domain they already own from the storefront settings page. Requests are processed manually at `/dashboard/admin/creator-domains`; after the team attaches the hostname to the deployment and verifies ownership, DNS, and TLS, marking it `ready` activates the root-domain storefront rewrite and creates an in-app notification. Pending domains never route to a creator. Product and share links remain on the canonical `adventskool.co.ke` origin so authentication and checkout stay trusted and consistent.
- Public creator storefronts use their own compact shop header instead of the global public header. Store search and the category drawer filter only that creator's published catalogue, categories are derived from the creator's live products, and courses, Digital Products, and Wealth resources are presented together under Products. The recommendation rail is always titled "You may also like" and deliberately mixes product kinds when inventory permits. Public bios preview the first 20 words with Read more/Read less controls; social links use platform-colored icon buttons.
